## WhatsApp OTP investigation (prod, mobile 81932999948)

Symptom: /whatsapp/send-code returned 000000 success and whatsapp_send_log has a row, but the
user reports not receiving the OTP.

Root cause class: the log only proves the provider ACCEPTED the submit request.
- `whatsapp_send_log.provider_success` column comment: "Whether the provider accepted the
  WhatsApp request" (see sql/create_pk_schema.sql ~line 319). No delivered_at / status column.
- ChuanglanWhatsAppSender logs only the RESPONSE (`WhatsApp API status=...body=...`), never the
  outgoing payload; whatsapp_send_log has no request_payload / recipient_number column.
- There is no WhatsApp delivery-report webhook or status-polling anywhere in the repo.
=> Cannot distinguish accepted vs delivered. Must query the provider delivery report using
   provider_message_id.

Outgoing payload contract (ChuanglanWhatsAppSender.buildPayload):
  wabaId, messageType=template, recipientNumber=countryDialCode+mobileNo, sendNumber,
  templateGroupId, language, bodyParams=[otpCode], buttonParams=[{type:text,value:otpCode}]
  The code always sends BOTH a body param and a button param with the same OTP; if the approved
  template has only one placeholder (or only a button), Meta rejects/drops the message even though
  the provider returned code=0 success.

Suggested hardening: log/persist the outgoing payload + recipientNumber + templateGroupId + param
count; add delivery_status updated via provider callback.

## Ops: how to unblock K000201 "Too many verification attempts. Please try again later."

That exact message is `DeviceSwitchLivenessLicenseRateLimiter.CLIENT_MESSAGE`, used by the public
endpoint `POST /auth/face/liveness-license` (AuthController:52 -> DeviceSwitchLivenessLicenseFacade).

Limits (pk-app/src/main/resources/application.yml:67-71, all env-overridable):
  max-invocations-per-ip     100 / 10 min   PK_AUTH_DEVICE_SWITCH_LIVENESS_LICENSE_MAX_PER_IP
  max-invocations-per-device   5 / 10 min   PK_AUTH_DEVICE_SWITCH_LIVENESS_LICENSE_MAX_PER_DEVICE
  window-minutes              10            PK_AUTH_DEVICE_SWITCH_LIVENESS_LICENSE_WINDOW_MINUTES
  block-minutes               15            PK_AUTH_DEVICE_SWITCH_LIVENESS_LICENSE_BLOCK_MINUTES

Redis keys (DB 0, no key prefix):
  pk:auth:device-switch-liveness-license:device:<deviceNo>:events          (ZSET, TTL window+1min)
  pk:auth:device-switch-liveness-license:device:<deviceNo>:blocked-until   (str epoch ms, TTL 15min)
  pk:auth:device-switch-liveness-license:ip:<ip>:events
  pk:auth:device-switch-liveness-license:ip:<ip>:blocked-until

Unblock: delete those keys (or just wait out the 15-min block TTL). Per-device limit of 5/10min is
very tight for manual testing.
Separate limiter to be aware of: DeviceSwitchLoginFaceAttemptLimiter ->
`pk:auth:device-switch-face-fail:<mobileNo>:<deviceNo>`, max 5 failures / 1 hour (default msg
"Too many requests", not the custom one).
clientIp resolution: X-Forwarded-For first hop -> X-Real-IP -> remoteAddr (AuthController:220,
duplicated in TrackingController:45 and OpsBackofficeAuthSupport:54).
No `server.forward-headers-strategy` / `tomcat.remote-ip-header` is configured in any yml, so
getRemoteAddr() is the raw TCP peer. Observed a limiter key `...:ip:127.0.0.1:events` => the caller
hit the app over loopback with no XFF/X-Real-IP (local test, or same-host proxy without
proxy_set_header). In prod the access log peer looked like 172.18.0.3 (another container on
pk-network), so the per-IP bucketing degrades to the proxy address, not the end-user IP. Two issues:
first-hop XFF is client-spoofable (or trust only the last hop added by our own proxy), and the per-IP
dimension collapses into one shared bucket.

Observed in local Redis: `...:device:bdee3055c0e537cb:blocked-until` = "1791446746428" (epoch millis,
= 2026-10-08 16:05:46 GMT+8, i.e. set 15 min earlier per block-minutes). `...:device:<uuid>:events`
had ZCARD 0. NOTE: two different deviceNo formats show up for the same tester - a UUID
(FBC19077-6C40-432F-BEC9-7384DE33A088) in the send-code log and a 16-hex id (bdee3055c0e537cb) here.
If the client is not stable about which deviceNo it sends, both the device-dimension rate limit and
the last_login_device_no exact-match "device switch" check will misfire. Worth confirming.

## Face ticket status boundary: VERIFIED_PENDING vs FAILED

All three 1:1 face facades decide the persisted status the same way (INCLUSIVE comparison):
  DeviceSwitchLoginFaceFacade:111/126, MobileChangeFaceFacade:71/88, BankCardAddFaceFacade:73/89
    boolean verified = similarity >= configLoader.loadAdvanceAi().faceThreshold();
    ... verified ? "VERIFIED_PENDING" : "FAILED"
So similarity >= threshold -> VERIFIED_PENDING; similarity < threshold -> FAILED.
Threshold source: app_config.advanceAiConf.faceThreshold (int); fallback OcrProperties.faceThreshold
default 60 (also livenessThreshold=60 but that is a DIFFERENT knob, used only by IdentityOcrFacade
for the KYC liveness score, never for this status). Because the compare is `>=`, exactly 60 passes
-> that is why a score of 60 yields VERIFIED_PENDING, not FAILED. To make 60 fail you need
threshold >= 61 (or change to strict `>`).
Third status value CONSUMED is set by the `consume` update after the ticket is spent; the
reusable-pending query filters status='VERIFIED_PENDING' AND expires_at > now.
In IdentityOcrFacade (KYC flow) faceThreshold/livenessThreshold are only RETURNED to the caller as
the threshold alongside the score - no status decision there.

The three login endpoints all validate credentials first and the face ticket LAST, immediately
before openSession (AuthServiceFacade):

  validateMobile -> password/deviceNo non-blank -> find user (K000214) -> find credential (K000213)
  -> passwordMatches (K000214) -> consumeDeviceSwitchFaceIfRequired:289 -> openSession -> updateLastLoginDeviceNo
- POST /auth/otp/verify -> verifyOtp -> verifyChallengeAndLogin:386-440
  validateMobile -> non-blank -> verify OTP challenge (not found/expired K000202, mobileNo mismatch
  K000202, deviceNo mismatch K000001, code mismatch K000202) -> findOrCreateActiveByMobileNo:433
  -> consumeDeviceSwitchFaceIfRequired:434 -> openSession
- POST /auth/login-whatsapp -> loginWithWhatsApp:346-384
  default-code branch: delete challenge:362 -> findOrCreate:364 -> consumeFace:365
  normal branch: same verifyChallengeAndLogin as OTP

consumeDeviceSwitchFaceIfRequired:714-716 = assertLoginAllowed then consumeFaceTokenIfRequired.
Both are no-ops when isFaceRequired() is false (no baseline, or deviceNo == last_login_device_no),
so the faceVerifyToken is ignored entirely in that case.
Expired/consumed ticket -> K000219 "Face verification required before login"
(LoginDeviceSwitchGateService:39/46/56/59). usableAt requires status='VERIFIED_PENDING' AND

## Mobile change (change phone number) order - OPPOSITE of login: face FIRST, OTP second

All steps require an authenticated principal (SecurityContextSupport.requirePrincipal), unlike the
device-switch face which is @PublicApi. Four steps:

0. POST /profile/identity/tongdun/liveness-license (+ /liveness-result) - authenticated TrustDecision
   license so the client SDK can produce a livenessId.
1. POST /profile/mobile/face/verify -> MobileChangeFaceFacade.verify
   requirePrincipal -> validateDeviceNo (X-Device-No REQUIRED, must equal body; K000017 if missing,
   K000001 if mismatched) -> requestId/livenessId/deviceNo non-blank -> resolveOrThrow baseline
   (no baseline => K000052) -> load baseline img -> retrieveLivenessResult (fail/no image =>
   OCR_LIVENESS_FAILED) -> store candidate -> compareFaces -> verified = similarity >= faceThreshold
   -> insert user_mobile_change_face_verification status VERIFIED_PENDING|FAILED, TTL =
   face_verify_ticket_ttl.mobileChangeMinutes (default 5) -> returns faceVerifyToken + expiresIn.
2. POST /profile/mobile/otp/send  (SMS) or /profile/mobile/otp/whatsapp/send -> MobileChangeOtpFacade.send
   new mobile valid -> load current -> newMobile == current => MOBILE_NUMBER_UNCHANGED ->
   newMobile owned by someone else => MOBILE_ALREADY_REGISTERED -> VALIDATE faceVerifyToken
   (findVerifiedByToken + userId + deviceNo + usableAt => else K000052) -> resend throttle per
   deviceNo (TOO_MANY_REQUESTS) -> daily cap (SMS: smsSendLog.countSince vs otpConfig.otpDailyLimit;
   WA: whatsAppSendLog.countSince vs whatsAppConfigLoader.loadDailyLimit) -> create challenge in Redis
   key auth:mobile-change:otp:token:<otpToken> (value userId|newMobile|deviceNo|faceVerifyToken|
   otpCode|expiresAt|channel) + resend key auth:mobile-change:otp:resend:device:<deviceNo> ->
   insert send_log -> send -> updateProviderResult -> failure deletes challenge + SERVICE_UNAVAILABLE
   -> markSent -> faceRepository.attachOtpToken(faceVerifyToken, otpToken).
3. POST /profile/mobile/otp/verify -> MobileChangeFacade.verifyAndChange (@Transactional)
   new mobile valid -> load challenge (missing K000202, expired => delete + K000202) -> FOUR-way match
   challenge.userId/newMobileNo/deviceNo/faceVerifyToken vs request => else K000206 OTP_TOKEN_MISMATCH
   -> verify otpCode (configured default code OR secureEquals => else K000202) -> RE-VALIDATE face
   ticket: findByToken + userId + deviceNo + ticket.otpToken == request otpToken + usableAt
   => else K000052 -> unchanged/registered re-checks -> updateMobileNo -> insert
   user_mobile_change_log (SUCCESS/USER) -> faceRepository.promote (=> status PROMOTED; false => K000202)
   -> userDeviceWriter.upsertFromRequest -> profileSyncOrchestrator.syncNow(MOBILE) -> 
   authServiceFacade.openSessionAfterMobileChange (new token pair) -> delete challenge.

Gotchas:
- The face ticket is bound to ONE otpToken by attachOtpToken (plain UPDATE, overwrites). So requesting
  a second OTP (resend, or SMS then WhatsApp) on the same face ticket invalidates the earlier OTP:
  step 3 passes the 4-way match but fails ticket.otpToken == request otpToken => K000052.
- Ticket status lifecycle differs per flow: mobile change uses VERIFIED_PENDING -> PROMOTED;
  device switch and bank card use VERIFIED_PENDING -> CONSUMED.
- FaceBaselineMapper.findLatestSuccessfulCompareByUserId picks the latest among MOBILE_CHANGE(PROMOTED),
  DEVICE_SWITCH_LOGIN(CONSUMED), BANK_CARD_ADD(CONSUMED) => the newly captured face becomes the
  baseline for the NEXT comparison (rolling baseline), KYC identity face is only the fallback.
- Both validateDeviceNo here REQUIRE the header (K000017) while AuthApplicationService's
  validateDeviceNoMatchesHeader merely skips when absent.

## Why credentials are checked before the face ticket (intended client flow)

`POST /auth/mobile/check` (PublicApi, AuthServiceFacade.checkMobileRegistration:203-224) is the
DISCOVERY step: it returns registered / accountStatus(EXISTING|NEW) / passwordSet / faceRequired.
So the client is meant to learn faceRequired BEFORE login, obtain the face ticket, and only then
call a login endpoint - where the face check is a pure VERIFICATION of that ticket. Rationale for
credentials-first at login:
1. Primary factor (password/OTP) vs step-up risk control (new-device face) - step-up only makes
   sense on top of a proven identity.
2. UX/error determinism: otherwise a typo'd password on a new device would send the user through a
   full liveness+face round trip (two external vendors) before being told the password was wrong.
3. Cost asymmetry: the face ticket is expensive to obtain and assertLoginAllowed only validates
   (consumeFaceTokenIfRequired consumes), both AFTER credentials => a wrong password does not burn
   the face ticket, so the user can retry with the same ticket.
4. Anti-probing is only defense-in-depth: mobile/check already exposes registered/faceRequired
   publicly, so enumeration is not actually prevented by the login ordering.
Asymmetry worth noting: the OTP IS consumed before the face gate (verifyChallengeAndLogin:430),
so a correct OTP + expired face ticket wastes the OTP while preserving the pricier face ticket.
